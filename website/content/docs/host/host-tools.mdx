## One concept, two callers

A host tool is a function that runs in the browser: navigate, scroll to a section, switch the theme, read the cart. You register it once on `VexaProvider` with a description and an input schema. From then on it can be called two ways:

| Caller | Path | Example |
|---|---|---|
| the model, as a tool call | "Take me to the catalog" becomes a call to `navigate` | model decides when |
| a button or `watch` in a spec | `{ "action": "runTool", "params": { "name": "navigate", "input": { "to": "/catalog" } } }` | the user decides when |

There is no separate concept for "page actions" or "events". An event is a tool that returns `{ ok: true }` and nothing else. For the screens you do not want to write a tool for, [Drive the page](/docs/host/admin) lets the model operate any accessible control through two generic tools.

## Declare a tool

```tsx title="tools.ts"
import { z } from "zod";
import { defineTool } from "vexa/react";

export const openCatalogItem = defineTool({
  description: "Scroll the catalog page to one component or example. item is the section id, for example bar-chart.",
  input: z.object({ tab: z.enum(["composed", "primitives", "interactive"]), item: z.string().min(1) }),
  run: ({ tab, item }) => {
    window.location.hash = `${tab}/${item}`;
    return { ok: true, summary: `Showing ${tab} › ${item}` };
  },
});
```

Register it on the provider under a name that matches `^[a-z][a-z0-9_]{0,63}$`: `tools={{ open_catalog_item: openCatalogItem }}`. The name is what the model and `runTool` buttons use.

## The HostTool type

```ts title="vexa/react"
type HostTool<I = unknown> = {
  description: string;
  input?: FlexibleSchema<I>;
  confirm?: boolean;
  run(input: I, ctx: HostToolContext): HostToolResult | Promise<HostToolResult>;
};

type HostToolContext = { toolCallId: string | null; source: "model" | "button" };

type HostToolResult =
  | { ok: true; summary?: string; data?: unknown }
  | { ok: false; error: string };
```

`description` is truncated to 300 characters before it is sent; write the first sentence for the model and put argument hints after it. `toolCallId` is `null` and `source` is `"button"` when a spec triggered the tool.

## Any schema library

`input` accepts an AI SDK `FlexibleSchema`: any Standard Schema implementation (zod 4, valibot, arktype) or a plain `jsonSchema()`. The provider converts it with `asSchema()` to produce the JSON Schema sent to the server and to validate the input before `run` is called. Invalid input returns `{ ok: false, error: "Invalid input: …" }` without running the tool.

```ts title="valibot and jsonSchema variants"
import * as v from "valibot";
import { jsonSchema } from "ai";

const setTheme = defineTool({
  description: "Switch the page between light and dark theme.",
  input: v.object({ theme: v.picklist(["light", "dark"]) }),
  confirm: true,
  run: ({ theme }) => {
    document.documentElement.classList.toggle("dark", theme === "dark");
    return { ok: true, data: { theme } };
  },
});

const reload = defineTool({
  description: "Reload the current page.",
  input: jsonSchema<{ hard: boolean }>({ type: "object", properties: { hard: { type: "boolean" } }, required: ["hard"] }),
  run: ({ hard }) => {
    window.location.reload();
    return { ok: true, summary: hard ? "Hard reload" : "Reload" };
  },
});
```

A tool with no `input` uses the second overload of `defineTool` and receives an empty object; the schema sent to the model is `{ type: "object", properties: {} }`.

## Typed pairs

`defineTool` infers the type of `run`'s first argument from `input`. A raw object literal in `tools={{ … }}` also works but leaves the input as `unknown`. The same idea applies to `contextSchema` and `context` on the provider.

## How a model call reaches the browser

1. On every request the client sends the JSON schema of its host tools in the body: `hostTools: [{ name, description, inputSchema }]`.
2. The server builds an AI SDK `tool()` for each one without an `execute` function, so the model can call it but the server never runs it. The description is fenced before it enters the prompt.
3. When the model calls one, the AI SDK ends the step and the tool call flows back to the client. `onToolCall` in `VexaChat` finds the tool in the provider registry, validates the input against its schema, runs it, and returns the result with `addToolOutput`.
4. `sendAutomaticallyWhen` resubmits the conversation so the model sees the result and finishes its answer. `stopWhen` on the server bounds the loop.

The whole round trip needs no shared file between client and server. The route stays generic.

## Host tools are read-tier by construction

`HostTool` has no `tier` field and the request body has none either. The server treats every host tool as read-tier: it never gates it with an approval card and it keeps host tools available even when the injection guard downgrades a turn. The reasoning: the code already runs in the user's browser, so a server gate would protect nothing. Anything that mutates data belongs in a server tool or an MCP tool, where the tier is decided on the server.

## Confirmation

`confirm: true` shows a card that names the tool and its description with Run and Cancel before the tool executes, whether the caller is the model or a button. When a chat is mounted the card appears above the composer; when a tool is triggered from a page button with no chat open, the provider shows its own tray in the bottom-right corner. A cancel resolves to `{ ok: false, error: "The user declined to run this tool" }`, which the model reports as "nothing changed". Use it for anything the user would notice: navigation, theme, opening windows, scrolling away from a form.

## Results under /tools

A host tool returns `{ ok: true, summary?, data? }` or `{ ok: false, error }`. The `summary` is one sentence the model can repeat to the user; `data` is structured output that specs can bind to. Every result is written to `/tools/<name>` in the state store of the spec that triggered it. The shape depends on the caller:

- From a button or `watch`: `data` when present, otherwise `{ ok: true, summary }`; on failure the whole `{ ok: false, error }`. `summary` or `error` is also copied to `/toast`.
- From a model tool call: the whole result object as returned by `run`, so `data` sits at `/tools/<name>/data`.

Bind with `{ "$state": "/tools/load_cities/cities" }` for the button path. The provider's `onToolResult(name, result)` callback receives every result regardless of caller, for logging.

## useVexaHost

Host code can run a registered tool through the same gate (input validation, confirmation, `onToolResult`) with the hook:

```tsx title="any client component"
import { useVexaHost } from "vexa/react";

const { runTool, tools } = useVexaHost();
await runTool("set_theme", { theme: "dark" });
```

`tools` is the list of `{ name, description, inputSchema }` descriptors sent to the server.

## WebMCP

`registerWebMcp(tools)` from `vexa/react` registers tools without `confirm` on `navigator.modelContext` when the browser provides it and returns an unregister function. It is independent of the provider and the demo does not call it.
